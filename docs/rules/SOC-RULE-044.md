# SOC-RULE-044: Password Spraying From One Source (distinct accounts correlation)

> Generated by `python scripts/rule_docs.py` from the rule and the test evidence.

**Level** high · **ATT&CK** T1110.003 · **Version** 1.0.0 · `rules/sigma/correlations/win_password_spraying.yml` · [Runbook](../runbooks/SOC-RULE-044.md)

## What it detects

One source IP fails to log on as ten or more different accounts within 30 minutes. Spraying slower than that (a few guesses per day) is still missed; that needs a long-window behavioural baseline, not a correlation rule.

## How it works

A **value_count** correlation: within 1800 s, grouped by `IpAddress`, it fires when the number of distinct values of `TargetUserName` is at least 10. One burst raises one alert. Base rules:

`failed_logon_for_spray` (Failed Network or RDP Logon for Spraying (base rule)):

- `selection`: `EventID` equals `4625` AND `LogonType` equals one of `3`, `10` AND `SubStatus` equals one of `0xc000006a`, `0xc0000064`
- `aggregated`: `FailedAttemptsCount` equals `None`
- condition: `selection and aggregated`

## Telemetry it needs

Windows Security log (Advanced Audit Policy) (logsource `windows/security`). If that source is not collected, the rule cannot fire: see [DATA_SOURCES.md](../coverage/DATA_SOURCES.md).

## Tuning

- Expected false positive: A shared jump host or VPN concentrator where many users mistype passwords (one NATed source IP).
- Expected false positive: Vulnerability scanners running authenticated checks with a wordlist of service accounts.
- Prefer an expiring exception for one known-benign pattern; change the logic (with a version bump) only when it is wrong for everyone. See [TUNING.md](../TUNING.md).
