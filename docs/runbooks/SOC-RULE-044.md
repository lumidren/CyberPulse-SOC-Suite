# Runbook: SOC-RULE-044 Password Spraying From One Source (distinct accounts correlation)

> Generated by `python scripts/rule_docs.py` from the rule, its playbook and the containment
> catalogue. Edit those sources, not this page.

## What fired

One source IP fails to log on as ten or more different accounts within 30 minutes. Spraying slower than that (a few guesses per day) is still missed; that needs a long-window behavioural baseline, not a correlation rule.

- Severity: **HIGH** · ATT&CK: T1110.003
- Rule file: `rules/sigma/correlations/win_password_spraying.yml` · Data source: Windows Security log (Advanced Audit Policy)

## Triage

Playbook: `brute-force`.

1. Check whether any targeted account logged on successfully from the same source afterwards
2. Confirm the source IP is not a known scanner, VPN concentrator or jump host
3. Review lockout events (4740) for the targeted accounts

Fields to check in the event: `EventID`, `FailedAttemptsCount`, `LogonType`, `SubStatus`.

## Response

- Proposed action: `BLOCK_SOURCE_IP_FIREWALL` (TIER_1_AUTO_ELIGIBLE, approval unless opt-in automatic mode, rollback FULL).
- What it does: Adds a perimeter drop rule for one source IP (pfSense / iptables).
- How it can go wrong: Blocking a shared address (VPN, NAT, CDN) cuts off legitimate users; an attacker changes IP and the block only adds noise; the firewall API is down so the block silently does not exist.
- Before approving: collect or check the volatile evidence package on the incident; confirm the target is not a protected asset or account.

## Known false positives

- A shared jump host or VPN concentrator where many users mistype passwords (one NATed source IP).
- Vulnerability scanners running authenticated checks with a wordlist of service accounts.

## Escalate when

- The activity continues after containment, or appears on a second host or account.
- A protected asset, privileged account or production service is involved.
- You cannot rule out real attacker activity within the playbook's steps.
