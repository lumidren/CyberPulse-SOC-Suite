# Runbook: SOC-RULE-008 Active Directory Replication Abuse (DCSync) via Non-DC Account

> Generated by `python scripts/rule_docs.py` from the rule, its playbook and the containment
> catalogue. Edit those sources, not this page.

## What fired

Detects directory replication service requests (DS-Replication-Get-Changes) originating from non-domain controller accounts, indicative of Mimikatz lsadump::dcsync credential harvesting.

- Severity: **CRITICAL** · ATT&CK: T1003.006
- Rule file: `rules/sigma/win_dcsync.yml` · Data source: Windows Security log (Advanced Audit Policy)

## Triage

Playbook: `credential-theft`.

1. Identify the process and account that accessed the credential material
2. Collect the volatile evidence package before approving any isolation
3. List accounts with sessions on the host; plan password resets for exposed accounts
4. Check domain controllers for follow-on use (4624 logon type 3/9, 4769 from the same source)

Fields to check in the event: `AccessMask`, `EventID`, `Properties`, `SubjectUserName`.

## Response

- Proposed action: `ISOLATE_ACCOUNT_AND_REVOKE_REPLICATION_PRIVILEGES` (TIER_3_IDENTITY, always needs approval, rollback FULL).
- What it does: Removes directory-replication rights from an account and locks it.
- How it can go wrong: Removing replication rights from a real domain controller or sync service breaks replication.
- Before approving: collect or check the volatile evidence package on the incident; confirm the target is not a protected asset or account.

## Known false positives

- Azure AD Connect synchronization accounts with explicit replication rights

## Escalate when

- The activity continues after containment, or appears on a second host or account.
- A protected asset, privileged account or production service is involved.
- You cannot rule out real attacker activity within the playbook's steps.
