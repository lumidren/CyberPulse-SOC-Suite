# Runbook: SOC-RULE-009 Suspicious AWS STS AssumeRole Abuse Across External Account

## What fired

Detects suspicious AWS STS AssumeRole calls originating from unapproved foreign IPs or anomalous role ARNs, characteristic of cloud privilege escalation and cross-account lateral movement.

- Severity: **HIGH** · ATT&CK: T1548, T1078.004
- Rule file: `rules/sigma/cloud_aws_assumerole_abuse.yml` · Data source: AWS CloudTrail (management events)

## Triage

Playbook: `cloud-identity`.

1. Confirm the sign-in or API call with the user or workload owner out of band
2. Review the identity's other activity in the same window (CloudTrail / Entra audit logs)
3. If confirmed, revoke sessions and rotate credentials; record the scope of access

Fields to check in the event: `eventName`, `eventSource`, `requestParameters.roleArn`, `sourceIPAddress`.

## Response

- Proposed action: `REVOKE_AWS_STS_SESSION_AND_ATTACH_DENY_POLICY` (TIER_3_IDENTITY, always needs approval, rollback PARTIAL).
- What it does: Attaches a deny-older-sessions policy to an IAM principal, invalidating active sessions.
- How it can go wrong: CI/CD pipelines and workloads using the role fail until they re-authenticate.
- Before approving: collect or check the volatile evidence package on the incident; confirm the target is not a protected asset or account.

## Known false positives

- Authorized multi-account CI/CD deployment pipelines (e.g. Terraform / GitHub Actions runners)

## Escalate when

- The activity continues after containment, or appears on a second host or account.
- A protected asset, privileged account or production service is involved.
- You cannot rule out real attacker activity within the playbook's steps.
