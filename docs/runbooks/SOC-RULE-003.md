# Runbook: SOC-RULE-003 Suspicious Scheduled Task Creation for Persistence

> Generated by `python scripts/rule_docs.py` from the rule, its playbook and the containment
> catalogue. Edit those sources, not this page.

## What fired

Detects creation of a new Windows Scheduled Task containing suspicious script interpreters or web download strings.

- Severity: **HIGH** · ATT&CK: T1053.005
- Rule file: `rules/sigma/win_scheduled_task_persistence.yml` · Data source: Windows Security log (Advanced Audit Policy)

## Triage

Playbook: `default-triage`.

1. Confirm the alert against the raw telemetry in the incident record
2. Check whether the host, user or source IP appears in other open incidents
3. Decide true or false positive and record why in the analyst notes
4. If false positive, propose a rule exception (rules/exceptions.yml) with an owner and expiry

Fields to check in the event: `EventID`, `TaskContent`.

## Response

- Proposed action: `REMOVE_SCHEDULED_TASK` (TIER_2_HOST, always needs approval, rollback FULL).
- What it does: Exports, then deletes or disables the malicious scheduled task.
- How it can go wrong: A legitimate maintenance task with similar content is removed; the attacker has other persistence, so removal gives false comfort.
- Before approving: collect or check the volatile evidence package on the incident; confirm the target is not a protected asset or account.

## Known false positives

- Legitimate software installers creating scheduled update tasks with network installers.
- Exception `EXC-0002` in force until 2027-04-30: IT's weekly maintenance task, created by the patching service account and running a script from the admin-only C:\Scripts\ folder.

## Escalate when

- The activity continues after containment, or appears on a second host or account.
- A protected asset, privileged account or production service is involved.
- You cannot rule out real attacker activity within the playbook's steps.
