# Runbook: SOC-RULE-006 Rapid File Encryption and Ransomware Canary Modification

> Generated by `python scripts/rule_docs.py` from the rule, its playbook and the containment
> catalogue. Edit those sources, not this page.

## What fired

Detects suspicious mass file creation with known ransomware extension patterns (.locked, .encrypted, HOW_TO_DECRYPT) targeting canary decoy directories.

- Severity: **CRITICAL** · ATT&CK: T1486
- Rule file: `rules/sigma/win_ransomware_canary.yml` · Data source: Sysmon Event 11 (file create)

## Triage

Playbook: `ransomware`.

1. Page the incident lead immediately; ransomware is time-critical
2. Confirm scope - which shares and hosts show encrypted files or deleted shadow copies
3. Approve or reject the proposed isolation within minutes, not hours
4. Verify backups are offline and intact before any restore

Fields to check in the event: `TargetFilename`.

## Response

- Proposed action: `KILL_RANSOMWARE_PROCESS_AND_RESTORE_VSS` (TIER_2_HOST, always needs approval, rollback PARTIAL).
- What it does: Graceful-then-forced kill of the encrypting process and restore from shadow copies.
- How it can go wrong: A backup or sync tool that writes many files is killed; shadow copies were already deleted, so restore fails; restoring overwrites files a user changed legitimately.
- Before approving: collect or check the volatile evidence package on the incident; confirm the target is not a protected asset or account.

## Known false positives

- Legitimate encryption software (e.g. VeraCrypt, 7-Zip encrypting explicit archives).

## Escalate when

- The activity continues after containment, or appears on a second host or account.
- A protected asset, privileged account or production service is involved.
- You cannot rule out real attacker activity within the playbook's steps.
