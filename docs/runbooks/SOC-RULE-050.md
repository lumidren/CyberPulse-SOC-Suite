# Runbook: SOC-RULE-050 Phishing Email Reported by a User or Failing DMARC with a Link or Attachment

> Generated by `python scripts/rule_docs.py` from the rule, its playbook and the containment
> catalogue. Edit those sources, not this page.

## What fired

A delivered message that a recipient reported as phishing, or that failed DMARC and carries a link or attachment. Message metadata only (Microsoft 365 EmailEvents style); no bodies.

- Severity: **HIGH** · ATT&CK: T1566.001, T1566.002
- Rule file: `rules/sigma/email_phishing_reported_or_auth_fail.yml` · Data source: Microsoft 365 email events (message trace / Defender for Office)

## Triage

Playbook: `phishing`.

1. Review the phishing triage (headers, sender, links) attached to the incident
2. Search for the same sender, subject or URL in other mailboxes and add them to the case
3. If anyone clicked or replied, check their sign-ins and reset the password if credentials were entered
4. Approve quarantine; release the message (rollback) if it turns out to be legitimate

Fields to check in the event: `AttachmentSha256`, `AuthenticationResults`, `DeliveryAction`, `ReportedByUser`, `Urls`.

## Response

- Proposed action: `QUARANTINE_EMAIL` (TIER_2_HOST, always needs approval, rollback FULL).
- What it does: Moves one message to a quarantine folder via Microsoft Graph.
- How it can go wrong: A legitimate but unusual email (invoice, HR notice) is hidden from its recipient; copies in other mailboxes are not touched.
- Before approving: collect or check the volatile evidence package on the incident; confirm the target is not a protected asset or account.

## Known false positives

- Newsletters and SaaS senders with broken DMARC alignment
- Users reporting legitimate but unexpected mail

## Escalate when

- The activity continues after containment, or appears on a second host or account.
- A protected asset, privileged account or production service is involved.
- You cannot rule out real attacker activity within the playbook's steps.
